# Migrations Guide

This directory is Alembic-owned (`backend/migrations/`). Its purpose is to
record schema state derived from the application models — never to invent it.

## Models first, then autogenerate

Every database schema change MUST start in the SQLAlchemy models files, never
as a hand-written migration or raw SQL:

1. **Edit the models first** — the change belongs in the feature's model file
   (`backend/app/systems/<capability>/models.py`). New model classes must also
   be registered in `backend/app/core/database/model_registry.py`, or Alembic's
   autogenerate cannot see them.
2. **Autogenerate the revision** — from `backend/`, run
   `uv run alembic revision --autogenerate -m "<change>"`.
3. **Review the generated revision** — read it operation by operation against
   the models before applying. Watch for mishaps: dropped or renamed columns,
   unintended type changes, missing partial or expression indexes, constraint
   or foreign-key behavior changes, or anything autogenerate misrepresents.
   Fix the model (or deliberately adjust the revision) before proceeding.
4. **Apply and confirm sync** — `uv run alembic upgrade head`, then
   `uv run alembic check` (and a second autogenerate) must come back clean.

## Hard rules

- Never hand-write a migration file as the starting point of a schema change.
- Never change the database schema with raw SQL or the Supabase Data API and
  call it done — schema changes are expressed in the models and flow through
  Alembic.
- A migration that also needs RLS policies, grants, functions, or data
  backfills still starts from the model change; those extra operations are
  added deliberately on top of the autogenerated revision.
- Do not edit an applied revision.
