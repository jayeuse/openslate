# Repository Guide

## Rule zero: never run backend and frontend tests at the same time

Read and apply this before any other instruction, every time a task runs tests.

- **One heavy test side at a time.** Never run backend tests (pytest batches, coverage, shards, fullstack, smoke) while frontend tests (Playwright isolated or HTTP, the frontend build) run, or the reverse. Wait for one side to finish before starting the other. The development machine (4 performance cores) runs each suite 2–3 times slower and fails timing-sensitive tests at random when both run together.
- **Keep parallelism inside each side.** Backend coverage runs `tests.parallel_coverage --shards 3`; the frontend suite keeps its Playwright workers. Do not drop to `--coverage-stacks 1` or a single worker without a measured failure.
- **The pre-push gate runs with `--serial`:** `python3 scripts/prepush.py --base <base-ref> --serial`. It orders the frontend and backend lanes one after the other and keeps each lane's own parallelism.
- **Start nothing else beside a running heavy lane:** no focused tests, batches, or sample runs "to use the time". Wait for it to finish.

Correct: "Ran `prepush.py --base main --serial`: frontend lane alone, then backend coverage on 3 shards."
Wrong: "Ran prepush without `--serial`, so the frontend suite and backend shards ran at the same time."
Wrong: "While backend coverage ran, repeated three Playwright tests to check flakes."

## Highest-priority testing rule

- **Batch by work unit, never by edit or handoff.** Use focused tests for TDD or debugging; run one relevant batch when the work stabilizes. Reuse passing evidence, including worker results, until the relevant code or setup changes.
- **Run the pre-push gate only right before a push.** Until the user asks to push, or a push is the next step, run only the focused tests and batches for the changed files and their direct callers. Do not run `scripts/prepush.py`, the full backend coverage gate, fullstack acceptance, or the smoke suite. Correct: "Changed `files/service.py`; ran `tests/files` integration batch; gate deferred until push." Wrong: "Finished a review fix; running prepush to be safe."
- **Clean up disposables after a successful push.** Remove only what this work created and no longer needs: runner-owned disposable stacks (Compose projects `openslate-e2e-*` and their containers, volumes, and networks), test processes and dev servers you started, and scratch files. Check ownership by Compose label and creation time; leave anything another session or an earlier date created. Keep runtimes and records that future work uses: the owned development Supabase stack (`openslate-supabase-local-*`) and its volumes, `.env`, installed dependencies, browsers, and Docker images, `.agent-runtime/` records, and the summaries under `backend/test-results/` and `frontend/test-results/`. Correct: "Push succeeded; removed three `openslate-e2e-<run>` stacks created by this gate; kept the dev stack and test summaries." Wrong: "Push succeeded; ran `docker system prune -a --volumes`."
- **Run each full suite once at its owning gate with sustainable concurrency.** The local pre-push gate runs the full suites: frontend static checks, all isolated and HTTP tests, and one production build; backend fast checks, the full coverage gate with its 90% overall/changed-line thresholds, and reset acceptance. Choose worker and disposable-stack counts from measurements on the development machine, and always run the gate with `--serial` (rule zero). Record actual runtimes. There is no mandatory total gate duration, and elapsed time alone does not reject a complete passing run. Preserve meaningful individual hang/deadline protections, all required scenarios, isolation, and cleanup guards. Documentation-only edits need no tests. Correct: "prepush passed all required checks serially; actual duration recorded." Wrong: "the machine was slow, so required suites or coverage checks were skipped."
- **Fix failures narrowly.** Rerun the failing case and affected batch, then only the failed gate. Never weaken assertions or use blind retries. Use isolated PostgreSQL for database guarantees and preserve runner guards.
- **Honor explicit test skips:** stop active runs, start no replacements, and report omitted checks. These rules override conflicting testing instructions in scoped guides, skills, and worker plans.

## Scope and architecture

- Read the nearest `AGENTS.md` before subdirectory work; it takes priority in its scope. Latest user instructions take priority. Read other scoped guides only when crossing their boundaries; use `docs/architecture/README.md` for architecture details.
- Root owns orchestration and documentation; run Python/uv/Alembic in `backend/` and npm/Playwright in `frontend/`.
- Command ownership is explicit: root `scripts/` is repository automation, `backend/operations/` is operator commands, and `frontend/tooling/` is npm-owned launch plumbing. Add no other product directory named `scripts`.
- Local development uses one owned Supabase Compose instance per worktree, with Supabase PostgreSQL, Auth, Storage, Studio, and Mailpit, plus host-run FastAPI and a local-only Next.js development server. Next is the daily browser origin and proxies `/api` to loopback FastAPI only in development. With a loopback FastAPI bind, `ENVIRONMENT=development` accepts the Next origin on localhost or a loopback, private, or link-local IP at `FRONTEND_DEV_PORT`; the development policy relaxes local transport controls. `ENVIRONMENT=test` and production-level Caddy/full-stack runs retain strict origin, host, response-header, request-body, concurrency, and rate-limit checks. Caddy is reserved for production deployment and explicit production-level acceptance. Production has one FastAPI application upstream serving the static Next export; it has no Node.js or frontend server process. Supabase Database is PostgreSQL; there is no pgweb or standalone root PostgreSQL service. Private file bytes live in Supabase Storage and are accessed through FastAPI.
- Supabase Auth authenticates email identities and issues provider tokens. FastAPI verifies and binds provider subjects to local profiles, owns application authorization and revocable sessions, and mediates Storage access and authenticated SSE. Alembic owns only the OpenSlate application schema; Supabase owns its Auth and Storage schemas. Supabase Realtime is deferred; SSE continues to use PostgreSQL `LISTEN`/`NOTIFY`.
- The intended server deployment is one Docker Compose stack per client on Linux or Windows Docker Desktop with WSL2/Linux containers. Windows runtime acceptance is pending. macOS workstation development remains allowed; macOS is not a supported server target. See `infra/supabase/README.md` and `infra/supabase/PLAN.md` for operator contracts and release gaps.
- Backend `app/core/` owns infrastructure, `app/common/` shared application code, and `app/systems/<page>/<capability>/` domain behavior. Active capabilities are grouped under `access`, `sandbox`, `openview`, `boards`, `manage`, and `platform`; `comms` remains reserved. Package location does not make cross-domain audit or lifecycle behavior page-restricted.

## Task scope and approval

- Before editing, define outcome, non-goals, expected files, and narrowest proof; inspect relevant implementation, tests, configuration, and instructions.
- Use the requested CLI/SSH/API access path; use UI automation only when that path is unavailable or UI operation is requested.
- Fix the root cause, reuse helpers/patterns/tests, remove replaced code unless compatibility is requested, and recheck the problem. Avoid speculative abstractions, compatibility layers, future schemas/options/services, and unrelated cleanup; abstract only for a current requirement or second real caller.
- Prefer existing libraries/components; needed dependencies may be installed without separate approval, but keep them relevant and verify integration.
- If adding an abstraction layer, configuration surface, roughly more than five files, or a speculative option, stop and reduce the design first.
- Read-only discovery needs no approval. Obtain approval for scope expansion, unrelated files, new services, unrequested public API/schema/storage/wire-format changes, data deletion, overwriting user work, discarding uncommitted changes, or rewriting Git history; preserve unrelated edits.
- VibeGuard U-17/U-29 applies only to real error paths in scope, never as justification for extra validators or compatibility layers.

## Setup and security

- Require Python `>=3.12,<3.15`, Node `>=24`; use `backend/uv.lock` and `frontend/package-lock.json`.
- Root setup: create owner-only `.env` from `.env.example` for a fresh development instance, generate installation keys with `backend/operations/supabase_keys.py --output <new-private-path>`, then start the owned Supabase development stack with `./scripts/dev.py db`. Keep existing volumes and credentials; this fresh-start path does not import legacy data. Treat connection strings and credentials as secrets.
- Backend setup: from `backend/`, run `uv sync --locked`, `uv run python operations/provision_database_role.py`, `uv run alembic upgrade head`, `uv run alembic check`, and `uv run python operations/provision_storage.py`; serve with `uv run python -m app --reload`. Start the API before bootstrapping the first administrator invitation so Auth can fetch its email template.
- Frontend: run `npm ci`, then `npm run dev`. The launcher parses root configuration for `FRONTEND_DEV_PORT`, `BACKEND_BIND_HOST`, `BACKEND_PORT`, and `PUBLIC_ORIGIN`; it passes only the three direct nonsecret values plus the derived exact HMR-origin hostname to Next, never the complete root environment or its secrets. `npm run build` produces the static export consumed by FastAPI.
- Do not reset provider volumes with `docker compose down -v`; they contain the installation database, Auth state, and Storage bytes. The local application-data reset is a separate guarded operation that uses Supabase Auth and Storage APIs. Backup and restore require the procedure in `infra/supabase/RESTORE.md`. A guarded disposable production Compose restore rehearsal using Linux containers on macOS Docker Desktop has passed; native Linux host boot/reboot and Windows restore acceptance remain pending.
- `DATABASE_BOOTSTRAP_URL` is the operator-only `supabase_admin` connection used to provision roles. `MIGRATION_DATABASE_URL` is Alembic's `openslate_owner` connection; `DATABASE_URL` uses the constrained `openslate_runtime` role. There is no pgweb inspector login. Never substitute SQLite or expose bootstrap credentials to application processes.
- Supabase Auth stores provider credentials and handles email invitations and recovery. FastAPI keeps the local user/profile mapping, account roles, access groups, and revocable `IdentitySession` records; encrypted provider refresh credentials stay server-side. Browser auth uses HttpOnly cookies plus CSRF protection; CLI clients use bearer tokens. Provider keys and connection strings stay out of browser code, tracked files, and reports.
- Application file bytes live in the private Supabase Storage `openslate-ready` bucket. FastAPI validates the file type (allowlist plus parsing in a bounded subprocess), stores the bytes, and marks the file ready in the same upload request; there is no antivirus scan. FastAPI enforces user access on download and serves bytes as attachments with `nosniff`. No local filesystem storage adapter is supported.
- Authorization uses one access function (`app/systems/access/policy/scope.py`): an account role is `admin`, `member`, or `guest`; an admin manages everything; members and guests get `read`, `write`, or `manage` on departments and modules only through group access rows, with the most specific row of each group winning and the highest level across groups; a guest is capped at `read`; no row means no access. A module the user cannot read is hidden (404).
- Mutations use `AuditSession` and individual ORM changes, never bulk/raw ORM mutations. Audit covers application ORM mutations only.
- Authenticated SSE carries opaque PostgreSQL `LISTEN`/`NOTIFY` invalidations without row snapshots. `/api/health` reports that the API process answers. `/api/ready` reports bounded database, Auth, Storage, and SMTP-configuration components, all required. SMTP readiness is configuration presence. A disposable production Compose rehearsal exercised bounded Auth and Storage failure/recovery; native host, Windows, and release acceptance remain separate. New installations enable permanent delete with `LIFECYCLE_PURGE_ENABLED=true`; the setting remains required, and existing installations retain their configured value.

## Security reporting and review rules

`SECURITY.md` is the security policy. Its section [Reference for automated tools](SECURITY.md#reference-for-automated-tools) holds rules SEC-R1 to SEC-R8, the known non-findings (NF-*), and the controls that reviews protect. Read that section before you report, review, or test anything security-related. The rules below restate the blocking ones; `SECURITY.md` wins if they differ.

- SEC-R1: Never put details of an unfixed vulnerability in a public issue, PR title/body/comment, commit message, branch name, code comment, or discussion.
- SEC-R2: Submit a vulnerability report only when the user tells you to, and only through GitHub private vulnerability reporting.
- SEC-R3: Never read, print, copy, or send secret values (`.env`, `.env*.local`, provider and application env files, backup repositories and their passwords, export passphrases, `docker compose config` output without `--quiet`). Variable names are fine.
- SEC-R5: Check the Out of scope table and the NF-* list before you report. A finding that needs `ENVIRONMENT=development` with a loopback bind host is not a vulnerability.
- SEC-R6: In code review, mark as P1 any change that weakens a control in the "Controls that reviews protect" table, unless the change states why.
- SEC-R8: Never send traffic to an installation other than a local stack that the user runs.

Correct: "Possible authorization bypass in `<path>:<line>` at `<commit SHA>`; drafted private advisory text for the user to submit."
Wrong: "Opened issue #<n>: '<route> skips the access check, here is the exploit.'"

## Verification and completion

- Review the final diff for correctness and scope; preserve unrelated work and remove task-created scratch code. Report actual results and blockers; deferred, skipped, or unavailable checks are unverified, never passed.
- Right before a push (see the testing rule above), run the canonical pre-push gate from the root with `python3 scripts/prepush.py --base <base-ref> --serial`; use `--list` to inspect its fail-closed change classification without running checks. It selects applicable backend, frontend, and unified server-image commands. Frontend-only changes run the frontend gate and rebuild the unified server image, but do not start PostgreSQL or full-stack work.
- Lower-level repair commands remain available: backend uses `uv run ruff check .`, `uv run mypy app operations`, and `COVERAGE_BASE_REF=<base-ref> uv run python -m tests.fullstack_runner --backend-coverage-only`; frontend uses `npm run verify`. Do not run these again after the canonical gate unless a failure invalidates that specific evidence.
- Record the base revision before implementation. Missing required evidence blocks normal push readiness unless the user explicitly overrides it. These scope limits take precedence over broader testing instructions; see [Testing Architecture](docs/architecture/16-testing-architecture.md) for runner details.

## Codex orchestration

- For implementation, troubleshooting, multi-agent work, or explicit evaluation, read `.agents/orchestration/PROTOCOL.md`; apply refresh-context → act → inspect-evidence → evaluate. If missing, report it and follow this guide without claiming full setup.
- Inherit parent model, effort, fallback, and approval settings from the active configuration; do not override them from this guide. Shared workers live in `~/.codex/agents/`; optional project overrides live in `.codex/agents/`; skills live in `.agents/skills/`. Read only relevant skills; repository rules/commands override mismatched generic examples.
- Handle small tasks directly; automatically delegate substantial bounded work when it improves quality or time. Do not duplicate verified discovery or assign the same investigation without distinct responsibilities.
- Planning-only requests produce investigation and a plan, not implementation. Parent owns decomposition, dependencies, difficult escalations, integration, conflict resolution, final review, and re-verification; choose workers by responsibility/complexity with domain ownership and applicable skills.
- Worker routing: `utility` = exact searches/inventories/prescribed checks; `explore` = repository tracing; `browser` = assigned live acceptance; `implement` = all delegated editing/test authoring; `analyst` = one difficult debugging, architecture, or security first pass. Use these exact roles: `explorer` is not `explore`; `general` is retired. Preserve role model/effort unless the user requests changes.
- Skill paths are `.agents/skills/<name>/SKILL.md`, resolved from root. Select by assignment; workers must read and report the paths themselves. React/Next.js: `react-frontend-patterns`, plus `query-cache-patterns` for cached server-backed reads; backend: `fastapi-backend-patterns`, plus `fastapi-api-design` for API contracts; database: `postgres-patterns`.
- Workflow skills: invoke `sdd-workflow` at the start of every new feature, bug fix, refactor, behavior change, or architecture decision to confirm scope and observable criteria; keep clear work inline without a spec file. Hand behavior criteria to `tdd-workflow` before implementation, then use `verification-loop` for actual checks. Documentation- and formatting-only work does not need SDD or TDD.
- Other skills: tooling → `project-tooling`; browser checks/test authoring → `playwright-e2e-testing`; security → `webapp-security-review`.
- For assigned UI visual-quality/accessibility review, add the available personal `frontend-design-review` skill. Plugin/personal skills complement project guidance only when relevant; do not load artifact skills for unrelated coding.
- A prescribed-check utility assignment does not authorize test-strategy selection. Browser assignments specify target, workflow, expected results, permitted interactions, and required evidence; unknown causes return to the parent.
- MCPs/plugins are inherited capabilities, not authorization. Use Context7 for unresolved library facts, project PostgreSQL for authorized evidence, and available browser tools for assigned live checks. If a skill expects an unavailable database MCP, report it and use the configured CLI or database path only when sufficient and authorized; do not install a substitute automatically.
- Follow the protocol assignment contract: objective, ownership, constraints, dependencies, acceptance criteria, evidence, skills read/reported, and stopping condition. Workers share the checkout: preserve others' edits, parallelize only disjoint writes, serialize conflicts, and do not delegate (`[agents] enabled = false`).
- Inspect worker diffs/results, reconcile findings, and retest fixes under the root testing rule. Continue incomplete workers with the precise remaining objective; do not restart discovery or equate unfinished work with a defect.
- Keep small task state in conversation; substantial multi-step work/handoffs use the protocol's Markdown run record in ignored `.agent-runtime/`. Record evidence as work happens and checkpoint before pausing; no runtime JSON schema required.
- Change persistent memory, create goals, or schedule continuations only when requested. OpenCode goal/VibeGuard hooks and turn limits are not migrated Codex enforcement.
- Context7/Playwright inherit global MCP settings (manage through Desktop Settings when available); PostgreSQL stays in project `.codex/config.toml`. Add no filesystem/sequential-thinking/memory MCP without demonstrated need.
- After local agent setup changes, run backend `uv run python ../scripts/agent-task.py doctor`; it checks workflow assets/configuration, not application acceptance or approval enforcement.
- Do not claim background scheduling, automatic retries, per-worker cost tracing, or isolated worktrees unless actually used and verified; follow the protocol for manual maintenance reviews.
