## Supported findings

### Priority 1: required corrections

1. **[P1][BLOCKING] Protect built-in role grants (CTRL-15).** The [role PATCH route](../../backend/app/systems/access/users/roles_router.py#L135) rejects a built-in name change but persists a permissions patch at line 144. An administrator can change Member or Administrator grants through the API although the approved built-in grants are immutable in the editor. Reject built-in permission changes at the route and verify a direct authenticated PATCH leaves the role unchanged. This gap existed in the base but remains an unmet approved Access criterion.

2. **[P1][BLOCKING] Apply the approved OpenView authorization boundary consistently (CTRL-20; CTRL-O03–O06, O12, O20, O23).** The live [Views adapter](../../frontend/src/components/systems/openview/adapters/views-api.ts#L862) and Chart adapters call record-query endpoints using the Access Workspace-policy [Reader dependency](../../backend/app/systems/sandbox/records/query_router.py#L43); aggregate-snapshot repeats that policy check after its snapshot. The [Access plan](../plans/access-functionality-plan.md#L11) excludes OpenView from this rule enforcement, while Report runs use the role-only boundary and can still export the same records. A role-authorized, Access-rule-denied user can run a Report yet gets 403 in Views/Charts. Use the established role boundary for the OpenView query routes, including the post-snapshot recheck, while keeping Sandbox CRUD policy protected; verify the denied-rule, role-authorized case across both surfaces. The correction must explicitly account for direct API clients receiving the same Record data through those OpenView routes.

3. **[P1][BLOCKING] Do not clear an authorized Board after a manage-only denial (CTRL-B03).** The always-rendered Manage Board control calls [handleDenied](../../frontend/src/components/systems/boards/components/server-backed-board-management.tsx#L718) when the user has VIEW but not MANAGE. The [parent callback](../../frontend/src/components/systems/boards/components/server-backed-boards.tsx#L584) then revokes the entire Board resource, so a permitted viewer loses the list and detail. Keep the manage-denied state inside that control; revoke Board state only when VIEW or authentication is actually lost. Verify VIEW-only and MANAGE users separately.

4. **[P1][BLOCKING] Keep Board access after a denied Record-choice query (CTRL-B08).** [Board placements](../../frontend/src/components/systems/boards/components/server-backed-board-placements.tsx#L465) treat a Sandbox Record-query 403 as Board-access loss via [the parent callback](../../frontend/src/components/systems/boards/components/server-backed-boards.tsx#L926). An Access rule may deny Record choices while the Board grant remains valid. Confine the failure to the Record picker and retain the Board, its placements, and navigation. Verify the mixed permission state.

5. **[P1][BLOCKING] Separate targeted-content authoring from recipient visibility (CTRL-B16, B19–B20).** [Announcement lookup](../../backend/app/systems/boards/announcement_service.py#L364) requires audience membership even for the author’s draft; the [editor](../../frontend/src/components/systems/boards/hooks/use-server-board-announcement-editor.ts#L655) creates a target-audience draft, immediately rereads it, receives 404, and clears the form. [Event lookup](../../backend/app/systems/boards/event_router.py#L153) similarly makes a creator-excluded Event unmanageable. A viewer target may lack Board write permission, leaving the item stranded. Give a creator access to that item’s editing context even when excluded from its recipient audience; keep ordinary feed, attachment, and inbox reads audience-gated and do not add a general Board-manager bypass. Verify the creator can manage targeted Events and Announcements without gaining recipient visibility.

6. **[P1][BLOCKING] Report actual reminder cancellation (CTRL-B15).** [Reminder DELETE](../../backend/app/systems/boards/reminder_router.py#L268) changes only PENDING work but also returns 204 after a worker has claimed RUNNING work; the UI announces “Reminder canceled.” The reminder can still be delivered. Return a conflict or another truthful state when cancellation did not occur, and verify the claim-versus-delete race with guarded scheduled work.

7. **[P1][BLOCKING] Restore the approved Dashboard widget set (CTRL-O16–O17).** The [Dashboard API schema](../../backend/app/systems/openview/dashboards/schemas.py#L30) accepts only chart widgets, and the [routed editor](../../frontend/src/components/systems/openview/components/server-backed-dashboards.tsx#L1452) offers only charts. CTRL-O16 retains summary, workload, record list, and chart widgets. Add the other three through the existing durable Dashboard contract and authorized live data paths; verify each type survives save/reload and respects audience and source-record access.

### Priority 2: required corrections

The new custom role has no grants. Copy effective displayed data grants without copying protected Administrator identity; verify the duplicate’s persisted permissions.

Deletion followed by name reuse makes an unrelated group appear as the old draft’s “current” server state; the role editor has an analogous fallback at line 348. Board grantee and Event/Announcement/Widget target paths also omit Access expiry, allowing unusable or unreachable targets. Apply the existing identity-eligibility predicate to chooser counts/pages, selected IDs, and target admission; verify status-active but expired users in both domains.

12. **[P2][BLOCKING] Allow authorized attachment reads on archived Boards (CTRL-B21).** [Board file authorization](../../backend/app/systems/platform/files/access.py#L99) requires an active parent even for reads, and [download loading](../../backend/app/systems/boards/attachment_service.py#L222) repeats the active-parent check.
