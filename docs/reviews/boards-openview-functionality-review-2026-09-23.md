## C. Findings

### P1 — high

**BR2-01 — Live Views cannot set ordinary sort or general grouping (incomplete CTRL-O05).** `frontend/src/components/systems/openview/page.tsx:514-517` sends ordinary Views URLs to `ServerBackedViewsWorkspace`, where new definitions start at `sort: []` (`components/server-backed-views-workspace.tsx:151-170`). That component never edits `definition.sort`; its only group selector sets Kanban lanes (`:1674-1706`). The earlier Views UI offered Sort and general Group records by (`page.tsx:2026-2061`). A user who needs a sorted or grouped Table cannot create that result in the live editor, even though the backend query contract supports it. Restore bounded sort and general group controls under the existing advanced View controls, preserving the six-layout page structure. Regression: create, save, reload, and query a multi-sort/grouped View using real records; assert order and group membership. Source inspection confirms the missing binding; rendered desktop/mobile Views showed no such control.

### P2 — medium

**BR2-02 — Live Views cannot edit saved presentation fields (incomplete CTRL-O07).** `components/server-backed-views-workspace.tsx:173-191` initializes column visibility/order, pins, density, wrapping, card size, and card title/detail fields, but the routed editor only exposes layout and lane/date selectors (`:1631-1888`). Those initialized values are read when rendering (`:608-660,2376-2385`), with no user action to change them. A new View is effectively locked to its first eight visible fields, and users cannot reproduce the previous layout-configuration workflow. Add the missing field/presentation controls within the existing advanced section and keep the current layouts. Regression: select a later field, reorder/pin it, save, reload, and verify the same visible presentation.

**BR2-03 — Record inspection loses filtered-order navigation and safe-link copy (incomplete CTRL-O12/O13).** Opening a live View row sets the `record` URL and switches to a record-only search (`components/server-backed-views-workspace.tsx:496-505`); the linked-record panel displays one card and a Return action (`:1210-1254,2181-2199`). Its `Previous`/`Next` controls at `:2443-2470` page the results table, not the inspected record. The previous inspector had per-record navigation and Copy safe link (`page.tsx:3995-4104`). A user inspecting a filtered result cannot step through adjacent matches or copy the inspected record's safe link. Restore inspector context over the authorized filtered order and identifier-only link action without changing the View query. Regression: inspect a record, cross a page boundary in both directions, copy the URL, and reopen the same record.

**BR2-04 — Choosing “Unsaved view” reselects the personal default (new CTRL-O10 interaction defect).** With a default configured, the chooser at `components/server-backed-views-workspace.tsx:1305-1330` navigates to a URL without `view` when “Unsaved view” is chosen. Selection immediately falls back to `defaultViewId` at `:419-457`, so the chooser jumps back to the saved View; an owner's next Save targets that View rather than a new draft. The synthetic rendered pass reproduced this: the URL dropped `view`, but the selection and “Equipment register” heading stayed on the default. Preserve an explicit local unsaved selection separately from the implicit default on a clean URL. Regression: set a default, choose Unsaved view, edit/save a distinct View, and confirm the default and original View remain unchanged. Another Save-as path is a workaround.

**BR2-05 — An owner cannot duplicate a saved View (incomplete CTRL-O09).** For an owned selected View, `saveTarget` is the existing View (`components/server-backed-views-workspace.tsx:687`); the dialog's Save path always chooses update (`:1595-1597,2621-2629`). The former Duplicate control in `page.tsx:1650-1670` is not available on the live route. Add a create-copy action that starts from the current definition/presentation and assigns a new ID; retain revision-checked update for Save changes. Regression: duplicate an owned View, assert two distinct IDs and unchanged original content after reload.

**BR2-06 — Dirty saved Views have no direct Reset changes action (incomplete CTRL-O11).** The live editor tracks its draft separately from `baseDraft` (`components/server-backed-views-workspace.tsx:448-459`) and guards navigation, but its View controls (`:1532-1627`) offer no direct reset to the selected saved revision. The prior Views screen exposed Reset changes (`page.tsx:1690-1710`). Users must navigate away or reconstruct their edits to revert an experiment. Restore a local discard/reset control using the existing draft state and guard; make no server write. Regression: edit a saved View, reset, and assert the original fields/query/presentation return without a mutation request.

**BR2-07 — Returning to a cached Dashboard widget can leave Refresh disabled (new CTRL-O15/O18 reliability defect).** In `components/server-backed-dashboards.tsx:585-631`, selecting a widget without a cached snapshot sets `snapshotLoading=true`. If a user returns to a previously cached widget before that request completes, the cached branch at `:594-600` returns without clearing loading; cleanup prevents the abandoned request's `finally` from clearing it. The Refresh button remains disabled and says “Refreshing…” (`:1823-1831`) until another navigation. Clear or key loading state for the newly selected cached widget while retaining the last-good snapshot. Regression: cache widget B, delay A's request, switch A→B, and assert B is visible and Refresh is enabled even when A later completes. Source-confirmed; this exact race was not run in the browser batch.

**BR2-08 — The current frontend HTTP test asserts the retired sample Dashboard (new test regression).** `frontend/tests/http/openview-charts.spec.ts:459-484` still expects a sample Dashboard label, browser-tab-only saving copy, and no API calls after navigating from Charts. The current route mounts `ServerBackedDashboards` (`frontend/src/components/systems/openview/page.tsx:518-520`). In this review's 53-test synthetic HTTP batch, this case failed at line 470; the captured page showed the real “Private dashboards” screen, while its unstubbed requests were directed to the deliberately unavailable synthetic backend port. Update only this route-boundary test to stub/assert the live Dashboard contract and retain the Reports sample assertion; do not change application behavior or weaken the outcome checks. Regression: rerun this file and the affected HTTP batch with zero failures.

Whether standalone test-mode invocations must independently repeat live ownership checks, beyond the runner-only trust boundary, remains a Phase 0 policy/verification question. No wrong-target write was observed or attempted.
- The plan assigns CTRL-O22 Chart Save/Reset to Phase 2 but places preferences in Phase 3; this review does not convert that milestone ambiguity into a defect. Board-manager audience bypass and archived-Board department detachment remain unapproved, so no finding assumes either behavior.
- The earlier concern that a UUID deep-link search may use a text cast/count is a source-level performance hypothesis, not a measured significant slowdown. No benchmark or realistic high-cardinality plan was run, so it is not ranked as a defect.
