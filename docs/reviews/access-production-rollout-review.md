## C. Findings

All findings are **BLOCKING** for their stated acceptance workflow. “Source-confirmed” means the trigger and failure follow the inspected code paths; runtime corroboration is stated where performed.

### P1 — High

**AR-01 — An expiry edit can remove the last usable administrator (new defect).**

- **Location/control:** `backend/app/systems/access/users/account_operations.py:125-141,182-188`; administrator profile/last-admin protection. `backend/app/systems/access/users/coordination.py:203-233,256-276,289-293` supplies the conflicting eligibility/count rules.
- **Trigger and evidence:** an administrator PATCHes an internal administrator's `expires_at` to a past instant, or schedules expiry while no other durable administrator remains. Internal profile validation returns before checking the expiry; the last-admin projection runs only for status/role changes. It also counts expired administrators as active. Authentication rejects expired identities (`backend/app/systems/access/identity/service.py:359-370`). A temporary executable unit probe confirmed that the sole-admin update commits an already-ineligible account. With two administrators, one expired account can falsely justify disabling/demoting the other.
- **Expected vs actual:** a change that would leave no eligible administrator should be rejected; the current update and count paths can allow it. **Smallest safe correction:** apply the authentication eligibility rule in the last-admin projection/count and guard expiry transitions, including future expiry that would leave no durable administrator. Preserve intentional expiry for accounts when another eligible administrator remains. **Regression:** sole-admin past/future-expiry PATCH and demotion/disable when the other administrator is expired.

**AR-02 — Deleted default role or closed default department disables every new invitation (new integration defect).**

- **Location/control:** `backend/app/systems/access/users/roles_router.py:151-168`, `backend/app/systems/sandbox/lifecycle/execution.py:175-190`, `backend/app/systems/access/policy/service.py:350-370,449-475`; creation defaults, role deletion, and department close.
- **Trigger and evidence:** a custom role is configured as the default and then soft-deleted while it has no assigned users/services; role deletion checks assignments but not `AccessPolicyDefaults.default_role_id`. Independently, Sandbox can soft-close a default department without checking `AccessDefaultDepartment`. Foreign keys only protect physical deletion. Every invitation calls `load_creation_defaults` first (`backend/app/systems/access/users/service.py:173-187`), which rejects either inactive reference even if the invitation supplies an explicit active role or departments. Two temporary guarded PostgreSQL integration probes executed the real role-deletion and department-close paths and observed defaults become unavailable in both cases.
- **Expected vs actual:** lifecycle actions should leave creation defaults valid, or give a clear blocked action with a repair path; currently invitation creation fails until an administrator manually changes defaults or restores the resource. **Smallest safe correction:** guard deletion/close when the resource is an active default, using a compatible lock order with defaults updates; keep current defaults and invitation semantics. An alternative atomic reassignment/removal needs a product decision, not an implicit migration. **Regression:** set each default, attempt the respective lifecycle action, and verify subsequent invitation creation remains available; include concurrent defaults-change/lifecycle coverage.

**AR-03 — Some valid email invitations have no UI completion path (new defect).**

- **Location/control:** `frontend/src/components/systems/access/state/controller.tsx:782-788,1104-1116`; invite action. `backend/app/systems/access/users/schemas.py:128-139` requires a three-character username, and `backend/app/systems/access/users/models.py:61-64` requires uniqueness.
- **Trigger and evidence:** `jo@example.com` produces a rejected two-character username; `ana@one.example` and `ana@two.example` produce the same username. The editor exposes email but no alternate username. The corrected authenticated Access browser probe observed the short-email rejection; the same-local-part collision follows from the derivation and unique database constraint. A valid email therefore cannot be invited in either case through this UI.
- **Expected vs actual:** an administrator should be able to complete an invitation for a valid, distinct email; the client rejects the short-local case or the server rejects the collision. **Smallest safe correction:** provide a valid unique candidate and a simple collision-recovery path (or have the backend assign it), while preserving the email-first low-technical-knowledge flow and current invitation delivery. **Regression:** short local part and same local part across two domains, including retry/reload.

### P2 — Medium

**AR-04 — Editing a default group fails while it contains a pending invite (new defect).**

- **Location/control:** `backend/app/systems/access/policy/service.py:159-204`; group membership. Invitation creation inserts pending users into default groups at `backend/app/systems/access/users/service.py:220-235`.
- **Trigger and evidence:** an administrator submits a default group's existing pending invite alongside one newly added active member. `replace_group_members` validates *all* desired IDs as active before distinguishing unchanged memberships, so it returns 409. A temporary executable unit probe reproduced the 409 with an unchanged pending member plus a valid active member; an exact no-op can fail for the same reason.
- **Expected vs actual:** existing pending memberships should remain while a valid group edit succeeds; currently the group is effectively uneditable until the invite completes or is removed. **Smallest safe correction:** validate newly added IDs against active-user eligibility while allowing unchanged pending IDs, without allowing new pending members through the editor. **Regression:** default group with pending invite, no-op save, add/remove another active member, and rejection of a newly supplied pending ID.

**AR-05 — Person editor advertises group choices its save path rejects (incomplete control).**

- **Location/control:** `frontend/src/components/systems/access/components/identity-editor.tsx:941-972`; person/guest group checkboxes. `frontend/src/components/systems/access/state/controller.tsx:825-830,1102-1107` rejects group changes in updates and non-default create groups.
- **Trigger and evidence:** change a group checkbox during identity creation or edit, review, then Save. The client rejects the command rather than persisting the choice. The separate group editor is the functioning group-management path.
- **Expected vs actual:** an editable control should complete its advertised change or clearly direct the user to where it can be done; this one cannot. **Smallest safe correction:** either connect it to the existing group command, or render group membership as read-only with a clear route to the group editor. Preserve group management as an advanced capability; do not remove it wholesale. **Regression:** create and edit attempts with changed group membership, plus the chosen handoff to the group editor.

**AR-06 — Stale conditional writes enter an unhelpful retry loop (new defect).**

- **Location/control:** `frontend/src/components/systems/access/state/controller.tsx:1605-1621`, `frontend/src/components/systems/access/state/api.ts:982-1024`; group/default/service edits and error recovery. The shared formatter at `frontend/src/components/systems/shared/runtime/sample-async-state.ts:8-13` preserves only sample errors.
- **Trigger and evidence:** another administrator changes a versioned resource, then this user saves with an old `If-Match` value. The API's 412 is caught and replaced by “Could not apply this Access change. Try again.” No reload reconciles the stale ETag, so retrying Save repeats the failure. A 403 initial read also receives generic recovery wording.
- **Expected vs actual:** explain the conflict or permission issue and provide a path to review current state without silently discarding the draft; current feedback cannot resolve the conflict. **Smallest safe correction:** map the API status and refresh authoritative data on 412 while retaining the user's draft for comparison; give permission-specific guidance for 403. Preserve conditional writes. **Regression:** stale 412 save/reload/draft preservation and denied initial read.

**AR-07 — Expired service identities appear Active in directory and overview (new defect).**

- **Location/control:** `frontend/src/components/systems/access/state/authoritative.ts:409-421`, `frontend/src/components/systems/access/components/identities-view.tsx:79-94,180-183`, `frontend/src/components/systems/access/components/overview-view.tsx:88-94`.
- **Trigger and evidence:** a service's `expires_at` passes while stored `status` remains `active`. The backend returns expiry-aware `effective_status` (`backend/app/systems/access/service_identities/schemas.py:20-27`), but the mapper copies only stored status. Badge, filter, and active count therefore imply access that has expired.
- **Expected vs actual:** read displays should reflect effective expiry; current displays say/count Active. **Smallest safe correction:** use the backend effective status for display/filter/count while retaining stored status for edit commands, extending the display status type/label as needed. **Regression:** expired-service projection, directory filter/badge, overview count, and unchanged edit payload.

**AR-08 — Defaults offers Administrator even though the API forbids it (incomplete control).**

- **Location/control:** `frontend/src/components/systems/access/components/governance-dialogs.tsx:358-375`; default-role selector. `backend/app/systems/access/policy/service.py:430-437,449-453` rejects Administrator as a default.
- **Trigger and evidence:** select the visible `admin` option (the authoritative role label) and save; the same selection is submitted and the server rejects it. The corrected authenticated Access browser probe confirmed that the forbidden option is present.
- **Expected vs actual:** every offered default-role option should be valid; this one is never saveable. **Smallest safe correction:** filter the built-in Administrator role from this selector, preserving the Administrator role elsewhere. **Regression:** selector options and a successful member/custom-role default save.

**AR-09 — A fixed-date sponsor test now fails for the wrong reason (new test defect).**

- **Location/control:** `backend/tests/users/test_local_identity_memberships.py:219-238`; backend regression coverage for expired guest sponsors.
- **Trigger and evidence:** the test fixes `now` at 2026-09-22, sets guest expiry to the next day, and patches only `user_service.utc_now`. `validate_identity_profile` consults the real clock in `users/coordination.py:296`, so as of 2026-09-23 it raises “Guest identities require a future expiration” before checking the expired sponsor. The fresh full-suite run failed; the focused rerun independently reproduced the regex mismatch. This is a test defect, not evidence that the application accepts an expired sponsor.
- **Expected vs actual:** the test should deterministically reach and assert the sponsor guard; it now fails earlier on guest expiry and blocks the mandatory backend gate. **Smallest safe correction:** use a shared frozen clock or a safely future guest expiry while keeping the sponsor expired, then assert the sponsor-specific rejection. **Regression:** run that focused case and the affected backend batch before the final full gate; do not weaken the assertion.
