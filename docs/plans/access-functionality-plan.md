## Executive assessment and boundaries

This is the approved-scope control-by-control acceptance baseline for the seven-view Access rollout. The inventory's current-state column records the pre-finalization Draft 5 source snapshot; implementation work is underway in this isolated worktree, so those descriptions are not a live status report. It records what each control did at that checkpoint, what it should do, which existing FastAPI behavior supports it, and how to verify it. The inventory groups related fields and actions into 28 stable IDs; the conditional-control specifications below retain those IDs while naming important distinct inputs and consequences.

At the Draft 5 checkpoint, the page had Overview, People & services, Roles, Groups, Detailed rules, Check access, and Access reviews. Access read its people, roles, groups, defaults, service metadata, capabilities, departments, and rules from authenticated FastAPI routes. The rule scope catalog exposed Workspace only; the application stated that enforcement applied to Sandbox data and related files and automations, not OpenView, Boards, or OpenComms. Service identities could hold metadata and intended rules but could not sign in. These were the recorded product boundaries at that checkpoint, not future promises. See [domain architecture](../architecture/03-domain-architecture.md), [API architecture](../architecture/07-api-architecture.md), and [authentication and authorization](../architecture/08-authentication-authorization.md).

The later integration decision supersedes that surface boundary for Record data: a Workspace Access denial must prevent Record values from being queried or delivered through Sandbox, OpenView, Board Record pickers/widgets, and Report runs or downloads. Board grants and content audiences remain separate checks. The implementation and its acceptance evidence must establish this revised boundary before the rollout is marked complete.

The authoritative snapshot deliberately contains empty review, template, deleted-identity, and history collections. Bulk identity updates, formal review campaigns, policy import, and policy-history restore are unavailable. The identity editor's password-reset preview explicitly sends no email and changes no password. The overview's Recent changes section therefore has no authoritative Access history feed. A control that is disabled, local-only, or a no-op is not counted as working merely because its component code exists.

This plan preserves the seven-view navigation and recognizable page layout. It favors one clear primary task per view, plain labels, and progressive disclosure: routine search and status first; advanced filters, technical IDs, time windows, locks, and comparisons behind a secondary disclosure. Useful advanced controls remain available. Unsupported launchers should be hidden or replaced by a single clear availability message, not left as dead-end buttons. No new route, schema, migration, installer, or database service is approved for this baseline; the user selected the existing group DELETE behavior amendment described below. No numeric visual-preservation score is claimed; the plan proposes no broad structural redesign.

The CTRL-18 decision is to block deletion while a non-deleted rule targets the group; deleting the group's rules implicitly is not approved. The rollout retains the other server-backed tasks while simplifying their presentation. Formal review campaigns, bulk identity actions, policy transfer/history restore, and administrator password reset require separate capability decisions rather than decorative disabled controls.

The user chose a draft-preservation guarantee for browser Back/Forward and accepted reload across Chromium (Chrome/Edge), Firefox, and WebKit (Safari), and approved a user-keyed, tab-scoped draft journal for unfinished non-secret names/emails and policy settings. It must never store passwords, tokens, confirmations, or executable commands. No installer runtime is part of this plan.

### Status labels

- **Live, server-backed:** the control reads from or writes through a current FastAPI route.
- **Live, presentation-only:** it navigates, filters, sorts, or compares the authoritative snapshot without changing server data.
- **Partial:** some of the grouped behavior is live and another part is unavailable or misleading.
- **Unavailable:** the authoritative page disables the control or its command is rejected.
- **No-op:** the control opens an explanation but performs no requested operation.
