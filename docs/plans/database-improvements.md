# Database improvements

Status: approved (2026-10-31). Jay approved D1 to D12 as recommended; D13 and D14 are open. Phase 0 and Phase 1 are done on `database-improvements-1` (pull request 1).

Target: the same as [Product concurrency fixes](product-concurrency-fixes.md): one server with 8 cores and 16 GB, up to about 300 people active at the same time across all organizations. Data volume: the seven Large packs in one installation, which is the permanent development data.

## Purpose

The application schema is structurally sound, but three things degrade as data grows: queries that read whole tables to count or skip rows, tables that are never trimmed, and audit rows for internal queue state. This plan fixes the causes of those problems. It also closes the integrity gaps that the database does not enforce today. It does not change what the product does for a person, except where a decision below says so.

## Rules for every item

1. Measure first. Each fix starts from a query, table size, or catalog fact recorded in this plan, and ends with the same measurement repeated.
2. Change the schema only through a model and an Alembic migration. Never change the schema or the data directly in a database.
3. Create an index on a table that can be large with `postgresql_concurrently=True` inside `op.get_context().autocommit_block()`. A plain `CREATE INDEX` blocks writes while it builds.
4. Add a constraint to an existing table in two steps: `NOT VALID`, then `VALIDATE CONSTRAINT`. The first step does not scan the table; the second step does not block writes.
5. Write a failing-first test for each item at the lowest faithful layer. Use real PostgreSQL for constraints, locks, plans, and catalog facts. Use the existing statement-budget tests (`tests/relationships_integration/test_statement_budgets.py`) for read-count fixes.
6. Keep `AuditSession` and individual ORM mutations for every application change. The only exceptions are the model that decision D2 removes from audit, and the audit partitions that step 2.6 drops after a verified archive.
7. Keep the list response shape (`PaginationMetadata`) unless decision D1 changes it.
8. Run database tests alone. Never run them beside a sample run, a full suite, or the gate (rule zero).

Correct: `The audit list count read 2.1M rows; the capped count reads at most 10,001; the Harbor Large audit page went from 157 ms to 9 ms; test_audit_list_total_is_capped.`
Wrong: `Added indexes on every foreign key to be safe.`

Source: the development database on 2026-10-31, read only. It holds the seven Large packs (3.5 GB). `pg_stat_statements` and the table statistics were never reset, so call counts include the Large seeding runs. Use the mean times as the signal, not the call counts.

Realtime keeps its broadcast messages in daily partitions that it creates and drops itself; no replication slot exists, and `max_slot_wal_keep_size = 512MB` limits the write-ahead log that a stuck slot can keep; the `LISTEN/NOTIFY` queue is empty. `auth.users` and Slate Operations users match one to one. `pg_net` has no queued requests or stored responses. About 20 of 100 connections are open at idle.

## Acceptance criteria

| ID | Criterion |
|---|---|
| DBI-1 | On Harbor Large, every list page in Access, Sandbox, OpenView, Boards, Manage audit, and Comms runs its SQL in under 100 ms at p95. No unintended change: the response shape and the authorization result are the same. |
| DBI-2 | Comms member counts for the largest Harbor Large department take under 50 ms, with the same counts as today. |
| DBI-3 | A record save writes one `records` audit row and no trigger event rows (after D2). Each trigger run, each notification, and each record change an automation makes still writes its audit row. |
| DBI-4 | Succeeded trigger events and runs, and notifications, older than the D3 periods are gone after one sweep. Newer rows, and rows still pending or failed within their period, remain. |
| DBI-5 | Every table that has `is_deleted` and `deleted_at` rejects a mismatched pair. |
| DBI-6 | After a record purge, no notification points to that record. |
| DBI-7 | A transaction idle for longer than the limit ends, and its locks are released. A request that waits for a lock within the normal time still succeeds. |
| DBI-8 | The statement budgets in `test_statement_budgets.py` do not increase, and the new budgets set in Phase 3 hold. |
| DBI-9 | A migration that creates an index on `audit_logs` or `relationship_edges` does not block record writes. |
| DBI-10 | The seal verify command reports no problem on an unchanged installation. When the owner role changes one audit row, removes one, or adds one to a sealed hour, the command names the organization, the hour and the kind of change. |
| DBI-11 | An audit month is dropped only after its archive passes the checksum check. An archived month can be loaded into a scratch database, and it passes the seal verify command there. If a check fails, the drop does not happen. |
| DBI-12 | Every audit query that the app runs (Manage audit list, actor, request, entity and department views, Boards activity, Comms settings history) returns the same rows after partitioning as before. |
| DBI-13 | A report keeps its latest 30 runs. An older run, with its output rows, notifications, eligible users and work rows, is gone after one sweep. The run's audit history remains, and its `csv_sha256` matches the SHA-256 of the CSV that a person downloaded. |
| DBI-14 | A succeeded trigger event holds no value copies. A failed event keeps them, and its retry evaluates the same values as the first attempt. |
| DBI-15 | The file check command reports no difference on an unchanged installation. It reports a removed object, an extra object, and a size difference, each with its bucket and file ID, and it changes nothing. |
| DBI-16 | When Slate Operations revokes a session, or the session reaches its limit, the provider session ends no later than the Auth limit. A short Auth outage still keeps the person signed in (product concurrency C2). |

## Phases

Order: integrity and safety first, because constraints are cheapest to add while tables are small. Bounded growth second, because smaller tables make every later query and index cheaper. Query paths third. Server settings last, because they must be sized against the finished query load.

| 2.5 | F15 | Seal the audit every hour (D8, approved).
