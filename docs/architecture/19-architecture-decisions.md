# Architecture Decisions

> **Scope:** Current data, identity, storage, runtime, and deployment decisions.

| Decision | Rationale | Consequence and current boundary |
| --- | --- | --- |
| Use self-hosted Supabase per client, with Docker Compose first | Each client gets its own provider data, Auth users, Storage bytes, credentials, and network boundary. Compose is the selected first operating model for Linux and Windows servers. | Checked-in base, development, and production Compose files define the deployment. Windows Docker Desktop/WSL2 startup, reboot, and restore acceptance is pending. macOS remains a development workstation and is not a supported server target. |
| Keep PostgreSQL as the relational engine | Supabase Database is PostgreSQL; changing its distribution does not justify changing ORM, query, or schema semantics. | SQLAlchemy transactions, PostgreSQL `LISTEN`/`NOTIFY`, and Alembic remain. Alembic owns application objects; Supabase initialization owns provider objects. The separate vanilla PostgreSQL/pgweb stack and inspector role are removed. |
| Supabase Auth establishes identity; FastAPI authorizes application access | Provider authentication should not turn Auth claims or metadata into application grants. Existing OpenSlate roles, groups, invitations, policy, and resource checks are the authorization authority. | A provider user ID must be explicitly bound to an eligible OpenSlate profile. FastAPI verifies provider credentials and liveness, creates revocable application sessions, and evaluates current permissions. Supabase metadata does not grant access. |
| Keep Studio as a provider operator interface | Operators need the Supabase service administration surface; pgweb is not part of the target stack. | Studio is more privileged than the former read-only pgweb connection, so its gateway path is loopback-only and authenticated. It does not replace application administration or FastAPI authorization. |
| Store file bytes in a private Supabase Storage bucket | Provider object storage supplies persistent per-installation bytes without a second local storage adapter. | `openslate-ready` remains private. FastAPI alone authorizes transfers. Browser clients never receive a Storage secret or direct object URL. |
| Validate file types instead of running antivirus | Background antivirus scanning made uploads wait, needed a large container and a signature supply chain, and slowed tests. | An upload is ready when its request finishes. An extension allowlist and a bounded parser subprocess admit only real PDF, PNG, JPEG, DOCX, XLSX, and PPTX files, and downloads are attachments with `nosniff`. Malware detection is left to each user's device. |
| Keep the current SSE invalidation contract | Opaque invalidations let clients refetch through the existing authorization boundary. A direct browser data channel would need a separate audience and revocation design. | PostgreSQL `LISTEN`/`NOTIFY` and authenticated SSE remain. Realtime is not started and no Realtime browser subscriptions or token endpoint are part of this phase. |
| Keep the unified FastAPI/static frontend server and Caddy ingress | Static export avoids a separate production Node server; Caddy supplies the HTTPS edge for the self-hosted stack. | Production Compose runs the unified API/static UI image and Caddy with provider services. Only Caddy is public; provider services, database, and API are not directly published. Runtime release acceptance remains separate from checked-in configuration. |
| Keep installation credentials split by responsibility | Provider bootstrap keys, application API settings, direct database logins, and backup credentials have different consumers and privilege levels. | Development uses a private root `.env`; production uses separate provider and application environment files plus a strict backup configuration. The browser receives none of those secrets. |
| Treat physical backup and restore as a controlled outage | PostgreSQL, Storage, Auth state, keys, and Compose configuration form one recovery set. Restoring only application rows or only file metadata would produce an incomplete installation. | Version 3 Restic backup captures stopped named volumes and selected private configuration. Restore targets a new project and instance ID, runs with ingress closed, invalidates OpenSlate application sessions, and finalizes against the target database identity. Physical restore and Windows acceptance remain pending. |
| Keep hosted deployment separate from this per-client stack | A self-hosted Compose installation does not create a managed SaaS or hosted deployment contract. | Hosted provisioning, registry publishing, secret delivery, DNS, support, retention, and managed-service operations remain separate future decisions; no hosted deployment is implemented here. |
