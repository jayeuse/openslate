# Audit and History

> **Scope:** Application ORM audit capture and post-commit invalidation.

`AuditSession` captures normal application ORM entity mutations and writes redacted minimal before/after snapshots in the same transaction as the business change. It records request and actor context when available. Work that runs as the workspace, such as a record trigger, has no user actor and names itself in `actor_label`. Bulk ORM mutation statements and raw ORM mutation execution are rejected because they cannot provide reliable per-row snapshots.

For department-owned entities, `manage/audit/department_ancestry.py` resolves the department before the ORM flush and `manage/audit/listeners.py` stores its ID with the audit row. This retains the department association even when a parent is hard-deleted in the same transaction. The audit column has no department foreign key, so the history survives a department purge. Company and project Board content and unrelated entities have a NULL department. `GET /api/audit-logs` allows administrators to list all entries or filter by department; a department manager must select a department where their department-level access is `manage`. Audit detail, export, and security-event routes remain administrator-only. Options: administrator and department manager (the manager for a department they manage, as for the list).

Record history for readers (S4, approved by the owner on 2026-11-03): any member may list the history of one record by sending `entity_id` without `department_id`, when the read check of `GET /api/records/{id}` passes (the module read of `app/systems/access/policy/scope.py`, shared through `app/systems/sandbox/records/access.py`). A record the member cannot open gives the same empty page as a missing ID. The reader sees only that record's entries and only readable fields: live fields of the record's module that are not audit-redacted, plus `is_deleted`. An entry with no readable change is left out in SQL, so the total stays right, and `request_method`, `request_path` and `note` are null. A reader gets 422 for any `search` and for sorting by request path, because both read values the page leaves out. Admins, and managers who select their department, keep the full snapshot. This is a deliberate widening through the one access function (SEC-R6).

Audit entries and security events can be found by the full `request_id` or by its last 8 characters, the error reference that the interface shows (`reference` on both lists, D7). The full ID uses `ix_audit_logs_request`; the 8-character search scans the rows of the bound organization (owner decision 2026-11-03: no expression index, because row-level security keeps PostgreSQL from using one for `right()`).

`audit_logs` is partitioned by month on `created_at`, in UTC ([`f43c7d0ee160`](../../backend/migrations/versions/f43c7d0ee160_audit_logs_monthly_partitions.py), decisions D4 and D20). Each month is a table named `audit_logs_y<year>m<month>`, and `audit_logs_default` holds any row with no month, so a missing month never stops an audit write. Every reader and writer names the parent. The primary key is `(id, created_at)`, because a key on a partitioned table must hold the partition column, so the database does not guarantee that `id` alone is unique across months; `AuditSession` is the only application writer and `id` is a UUIDv7. `ix_audit_logs_org_created_at_id` carries the row-level security filter in each month.

The scheduling worker calls `public.ensure_audit_partitions()` when it starts and every hour, outside any organization ([`worker.py`](../../backend/app/systems/platform/scheduling/worker.py)). The function takes no input, runs as `slateops_owner` and creates this month and the next two. It is the runtime's only path to DDL. It uses `ATTACH`, which leaves audited writes running. `ATTACH` also locks `audit_logs_default` and `organizations` for a short time, so the function sets `lock_timeout` to 500 ms. PostgreSQL applies that limit to each lock attempt: one call can wait more than once, and the limit does not bound how long a lock is held after it is granted. An attempt that reaches the limit ends the call with SQLSTATE `55P03`, and the call changes nothing. It skips a month that already has rows in `audit_logs_default` and returns the count of skipped months; those rows stay there and stay readable. A failed or skipped creation logs `operational_attention` once for each streak, with the reason `audit_partition_failed` or `audit_partition_skipped`, and the next timer tries again.

`audit_logs.performed_by` has no foreign key ([`635864bb4a1c`](../../backend/migrations/versions/635864bb4a1c_drop_audit_actor_foreign_key.py), decision D21), as `security_events.actor_id` has none. Removing a person never rewrites an audit row, so a removed person's id stays in the rows they wrote. The readers that name an actor (the audit list, its options and export, and Board activity) find no active member for that id and show no name; the export writes "Unknown person". Comms configuration history returns the id only.

### Audit seals

Each organization has one hash chain over its audit rows, and the installation (`org_id` NULL) has one ([`seals.py`](../../backend/app/systems/manage/audit/seals.py), [`b1b3908e844b`](../../backend/migrations/versions/b1b3908e844b_audit_seals.py), plan step 2.5, decision D8). An `audit_seals` row covers one UTC hour of one chain: the row count, a SHA-256 hash of the hour's rows, and a chain hash over the previous seal, the chain, the hour, the count and the row hash. Empty hours are sealed too, so a gap shows. A chain starts at the hour of its earliest row or, for an organization, of its creation if that is earlier.

- **Row form.** Version 1 hashes all 15 columns as one `jsonb` array in a fixed order: the time is UTC text with microseconds, and `before` and `after` are wrapped in one-element arrays, so SQL NULL and JSON `null` differ. PostgreSQL builds the text; the expression is a constant in the source, never a database function, so the database owner cannot change it. It names `pg_catalog` for every function and type, and the seal and verify transactions set `search_path = pg_catalog, pg_temp`, so a function that the owner creates in `public` cannot take a catalog function's place. The owner could still replace `public.audit_logs` with a view; `alembic check` reports that, so run it before a clean verify is trusted. Rows are ordered by `(created_at, id)`. The form survives `COPY` text, which is what a dump writes.
- **Writer.** The scheduling worker seals at start and every hour, or after 60 seconds while a backlog remains. It reads every `organizations` row, binds each in turn, then seals the installation chain with no binding. An hour is sealed once the worker's clock passes its end plus `SEAL_DELAY` (2 hours), because `created_at` is set by the API clock at flush and the transaction commits later. Each wake seals at most 168 hours of each chain, in transactions of up to 24 hours, under a transaction advisory lock for the chain. A duplicate `id` in an hour logs `audit_duplicate_id`; a failed pass logs `audit_seal_failed` once for each streak. The worker never continues a chain whose latest seal is off a whole hour or not yet past its horizon: it logs `audit_seal_failed` for that chain and seals the others.
- **Rights.** The runtime has `SELECT, INSERT` on `audit_seals` and no other right. Row-level security shows the bound organization's seals and the installation's, and the INSERT policy accepts only those chains and only an hour that has started by the database clock. A CHECK keeps every seal on a whole UTC hour, because the chain hash holds whole seconds. There is no UPDATE or DELETE policy.
- **Commit lag.** An audited transaction that commits 10 seconds or more after its first audit row logs `worker_metrics` with `audit_commit_lag` and the age. Past `SEAL_DELAY` it also logs `audit_commit_after_seal_delay`, because its rows can land in an hour that is already sealed.
- **Verify.** [`verify_audit_seals.py`](../../backend/operations/verify_audit_seals.py) recomputes every sealed hour as the runtime, one read-only snapshot for each chain, and reports the organization, the hour and the kind: `added`, `removed`, `changed`, `seal_missing`, `seal_changed`, `seal_misaligned`, `seal_in_future`, `rows_before_chain`, `unsealed`, `duplicate_id`, `head_mismatch` or `chain_absent`. It checks each seal on its own first: a seal off a whole hour or for an hour that has not ended is reported and holds no rows. Each remaining seal is compared with the rows of its own hour. A missing seal is reported two hours past the worker's horizon, and each run of missing or late hours reports at most 100. A hash finds the hour, not the row.
- **Chain heads.** The backup runner reads the latest seal of each chain through the backup bridge before it stops the services, and the archive keeps them as `audit/seal-heads.json`, a listed file of the bundle. `verify_audit_seals.py --heads` checks that each exported head still matches; `--write-heads` exports them by hand.
- **What seals prove.** Without a heads file, verify proves that rows and seals agree inside the database; an owner who rewrites both is not detected. With heads, it proves that nothing changed up to each exported head. A change after the latest exported head is not detected, so more frequent backups narrow that window. Organization removal deletes a whole chain; an older head then reports `chain_absent`, which is expected.
- **Migrations.** A migration never changes an audit row while seals exist: a changed row breaks its seal. Only the D21 downgrade does, after the seal downgrade has dropped every seal. The seal revision's downgrade drops every seal, and the next wake writes the same chain again for unchanged rows.

Audit capture includes application data mutated through FastAPI. It excludes Alembic, administrative direct SQL, database provisioning, and filesystem byte operations. These boundaries must remain explicit in operational reporting.

Some models set `__audit_enabled__ = False`, so their row changes write no audit row and queue no invalidation. Bulk mutations stay rejected on them. Queue and job state is outside audit: [`ScheduledWork`](../../backend/app/systems/platform/scheduling/models.py), the [Comms job models](../../backend/app/systems/comms/jobs/models.py), and [`RecordTriggerEvent`](../../backend/app/systems/sandbox/record_triggers/models.py). A trigger's runs, its record changes and its notifications stay audited. The output rows of a report are also outside audit: [`ReportRunRow`](../../backend/app/systems/openview/reports/models.py) and `ReportRunEligibleUser`. The audited `ReportRun` holds the row count and an unredacted `csv_sha256`, so a saved copy of the CSV can be proved after the sweep removes the run.

After a successful audited commit, the listener queues one or more opaque invalidation events and publishes them through PostgreSQL notification. The event payload identifies only safe entity scope and never contains row snapshots, credentials, filenames, or file bytes. Delivery is best effort: database and audit state remain canonical if an SSE listener is unavailable.

Audit history is not a backup, a security-information event stream, or a complete
record of host-level operations. A guarded encrypted backup and manual restore
foundation exists; supported customer recovery, automated backup scheduling and
installed-host observability remain pending deployment work. See
[Deployment Architecture](12-deployment-architecture.md).
